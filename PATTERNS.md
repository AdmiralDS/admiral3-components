# Паттерны разработки Admiral 3 primitives

Этот документ объясняет не только **как** писать компоненты в `@admiral-ds/admiral3-primitives`, но и **почему** в
проекте приняты именно такие решения. Он предназначен прежде всего для разработчиков, которые уже работали с
`@admiral-ds/react-ui` и видят в новом пакете больше файлов, типов и проверок.

Короткий ответ: новый пакет строится как набор небольших публичных primitives с заранее ограниченными контрактами.
Небольшая явность в исходном коде уменьшает число несовместимых API, случайных визуальных состояний и скрытых зависимостей
после публикации библиотеки.

Правила реализации и команды находятся в [CONTRIBUTING.md](CONTRIBUTING.md), структура репозитория — в
[PROJECT-MAP.md](PROJECT-MAP.md), тестовый контур — в [tests/TESTING_README.md](tests/TESTING_README.md). Здесь собраны
причины, стоящие за этими правилами.

## Это не копия `react-ui`

`react-ui` — зрелая библиотека с большой историей и накопленной обратной совместимостью. В ней можно встретить несколько
поколений API и реализации: строковые union-типы, большие `switch`, анонимные config-объекты, `cssMixin`, компоненты и
служебные сущности в одном `index.tsx`.

Новый пакет начинает публичный контракт с чистого листа и решает другую задачу:

- primitives должны быть небольшими и композиционными;
- допустимые состояния должны быть видны TypeScript и проверяться автоматически;
- дизайн-токены должны оставаться источником визуальных значений;
- внутреннее устройство компонента не должно случайно становиться публичным API;
- компонент должен одинаково проверяться в unit, browser и visual-контуре;
- точечный импорт компонента не должен притягивать остальную библиотеку.

Поэтому «в `react-ui` было короче» само по себе не является основанием повторять старый паттерн. Сравнивать нужно не число
строк в одном файле, а стоимость развития и поддержки публичного контракта.

### Краткая карта отличий

| В `react-ui` встречается                              | Целевой паттерн Admiral 3 primitives                                  | Зачем                                                                  |
| ----------------------------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Ручной строковый union отдельно от runtime-кода       | `as const`-массив и union, выведенный из него                         | Один список для типов, stories и тестов                                |
| `switch` с `default` для цветов и размеров            | Исчерпывающий `Record<Variant, Value>`                                | Новый вариант нельзя добавить без его значения                         |
| Анонимный custom-объект, например `{ background?: }`  | Именованный и экспортируемый `ComponentColorConfig`                   | Стабильный публичный тип, JSDoc и понятные ошибки                      |
| Публичный `cssMixin` как общий escape hatch           | Семантические props, композиция и CSS custom properties               | Меньше зависимости от внутренней CSS-разметки                          |
| Реализация, типы и стили в одном `index.tsx`          | `Component.tsx`, `types.ts`, `constants.ts`, `style.ts`, `index.ts`   | Явные ответственности и узкая публичная граница                        |
| CSS custom property собирается вручную в каждом месте | Общий `cssToken` и animation helpers                                  | Единая theme fallback-логика                                           |
| Storybook как основной runtime примеров               | Storybook для docs, отдельный playground для browser/e2e              | E2E не зависит от Storybook и проверяет consumer-like сценарий         |
| Доступность зависит от конкретного поколения API      | Нативный элемент, осознанные aria-defaults и обязательный a11y-контур | Предсказуемый keyboard, form и screen-reader контракт у новых controls |

## Зачем `ColorConfig`, если цвет всего один

Например, публичный API `BadgeDot` выглядит так:

```ts
export type BadgeDotAppearance = (typeof BADGE_DOT_APPEARANCES)[number];

export interface BadgeDotColorConfig {
  backgroundColor: string;
}

export interface BadgeDotProps extends HTMLAttributes<HTMLDivElement> {
  appearance?: BadgeDotAppearance | BadgeDotColorConfig;
}
```

Использование остаётся коротким:

```tsx
<BadgeDot appearance="info" />
<BadgeDot appearance={{ backgroundColor: 'var(--product-status-color)' }} />
```

### Почему не `appearance?: BadgeDotAppearance | string`

Произвольный `string` уничтожил бы закрытый набор preset-вариантов. TypeScript перестал бы ловить опечатки:

```tsx
// Должно быть ошибкой, а с `| string` стало бы допустимым значением.
<BadgeDot appearance="succes" />
```

Кроме того, строка была бы неоднозначной: это имя preset, CSS-цвет, имя токена или ошибочное значение? Объект явно
отделяет пользовательскую настройку от системного варианта.

### Почему не отдельный prop `color?: string`

Для `BadgeDot` preset appearance и пользовательский цвет — два взаимоисключающих способа задать одну и ту же визуальную
ось. Union выражает это прямо: передаётся либо системный вариант, либо custom-конфигурация. Отдельные `appearance` и
`color` потребовали бы правила приоритета для случая, когда переданы оба.

У более сложного `Button` ситуация другая: `appearance` и `colorMode` сохраняют семантику и поведение кнопки, а
`colorConfig` частично переопределяет несколько цветов и состояний. Поэтому там отдельный prop является осознанным
исключением, а не расхождением стиля.

### Почему объект оправдан даже с одним полем

1. **Сохраняется форма API между родственными компонентами.** У `BadgeDot`, `Pulse`, `Spinner` и `Badge` custom-ветка
   распознаётся одинаково, хотя число настраиваемых цветов отличается.
2. **Имя поля передаёт семантику.** `backgroundColor` точнее, чем безымянная строка или абстрактный `color`: понятно,
   какое CSS-свойство меняется.
3. **API можно расширить без смены формы значения.** Если дизайн позже добавит границу или отдельное состояние, объект
   допускает новый именованный ключ. Добавлять поле нужно только по реальной задаче, не заранее.
4. **Объект является безопасным runtime-разделителем union.** Реализация отличает preset от custom через
   `typeof appearance === 'object'` и не передаёт объект в DOM.
5. **Тип не увеличивает runtime bundle.** TypeScript-интерфейс исчезает после сборки. Цена паттерна — несколько строк
   исходного кода, а не JavaScript в браузере.

### Почему это отдельный экспортируемый interface

`BadgeDotColorConfig` — часть публичного API, поэтому у неё должно быть стабильное имя:

- имя видно в подсказках IDE и сообщениях TypeScript;
- тип можно импортировать для wrapper-компонента или собственной конфигурации;
- JSDoc попадает в декларации и документацию;
- форма не дублируется анонимно в props, styled props, тестах и пользовательском коде;
- по имени проще искать использования и обсуждать изменение API на review.

Технически `type BadgeDotColorConfig = { ... }` тоже мог бы описать объект. В этом проекте для публичных props и
config-объектов выбран единый шаблон с `interface`, чтобы структура компонентов была предсказуемой. Это соглашение, а не
утверждение, что `interface` всегда лучше `type`.

Не нужно создавать экспортируемый config-интерфейс для каждого временного объекта внутри функции. Паттерн относится к
именованной части публичного контракта.

### Почему поле обязательное

В `BadgeDotColorConfig` поле `backgroundColor` обязательное, потому что пустой объект не задаёт пользовательский цвет и не
имеет полезного смысла. У `ButtonColorConfig` поля опциональны: кнопка допускает частичное переопределение большой таблицы
цветов с fallback на preset. Обязательность определяется поведением компонента, а не единым механическим правилом.

## Закрытые варианты выводятся из constants

Для `appearance`, `dimension`, `status` и других конечных вариантов используется один runtime source of truth:

```ts
export const BADGE_DOT_APPEARANCES = ['neutral', 'info', 'error', 'success'] as const;
export type BadgeDotAppearance = (typeof BADGE_DOT_APPEARANCES)[number];
```

Массив нужен не только TypeScript. Его используют stories, параметризованные тесты и visual-матрицы. Если отдельно
написать union и отдельно список, они неизбежно могут разойтись.

Таблицы значений оформляются через исчерпывающий `Record`:

```ts
const colors: Record<BadgeDotAppearance, CssToken> = {
  neutral: neutralToken,
  info: infoToken,
  error: errorToken,
  success: successToken,
};
```

После добавления нового appearance TypeScript потребует добавить соответствующий цвет. В старом паттерне с `switch` и
`default` новый вариант мог незаметно получить fallback от другого варианта. Явная таблица превращает такое расхождение в
ошибку на этапе разработки.

Произвольный `string` для закрытых props запрещён не только соглашением: это проверяет `validate:components`. Custom
значения передаются отдельным объектом, а не расширяют словарь preset-имён.

## Публичные и styled props разделены

Потребитель работает с `appearance` и `dimension`, а `styled-components` получает `$appearance`, `$dimension` и
`$colorConfig`.

Префикс `$` означает transient prop. Такой prop участвует в вычислении стилей, но не попадает в итоговый HTML неизвестным
атрибутом. Разделение также не позволяет внутреннему удобству styled-компонента случайно диктовать внешний API.

`data-appearance` и `data-dimension` добавляются отдельно, когда состояние полезно для CSS, диагностики или browser-теста.
Custom-конфигурация обозначается стабильным значением `data-appearance="custom"`; сам объект в DOM не сериализуется.

Для boolean-маркеров атрибут присутствует только в активном состоянии:

```tsx
data-read-only={readOnly ? '' : undefined}
```

`data-read-only="false"` не используется: CSS-селектор `[data-read-only]` считает такой атрибут присутствующим и применит
неверное состояние.

## Компонент сохраняет нативный DOM-контракт

Props расширяют атрибуты подходящего HTML-элемента, а несовместимые поля исключаются явно:

```ts
interface ToggleProps extends Omit<React.InputHTMLAttributes<HTMLInputElement>, 'size' | 'type'> {
  dimension?: ToggleDimension;
}
```

Это даёт потребителю стандартные `name`, `value`, `form`, `aria-*`, `data-*` и обработчики без их ручного копирования в
наш API. Конфликтующий нативный `size` исключён, потому что размер design-system компонента задаёт `dimension`; тип input
фиксируется самой реализацией.

`forwardRef` направляет ref на полезный нативный элемент, а `displayName` сохраняет читаемое имя в React DevTools. Для
input-компонента ref должен попадать именно на `input`, чтобы работали focus, form libraries и imperative DOM API.

Интерактивный primitive использует нативный элемент (`button`, `a`, `input`) везде, где это возможно. Это дешевле и
надёжнее самостоятельной имитации клавиатуры, focus, form submission и accessibility через `div`.

## Дефолты не должны отнимать управление у потребителя

Размер по умолчанию для компонентов с размерами — `m`. Единый default убирает необходимость помнить исключения между
компонентами.

Дефолтные DOM- и accessibility-атрибуты задаются до `{...props}`, чтобы потребитель мог осознанно их переопределить.
Обязательные внутренние атрибуты, без которых ломается контракт компонента, ставятся после spread.

Например, декоративный `BadgeDot` по умолчанию скрыт от accessibility tree, но перестаёт быть декоративным, если задано
доступное имя. Явный пользовательский `aria-hidden={false}` также сохраняется. Это безопасный default, а не жёсткий запрет.

У disabled-ссылки, напротив, `aria-disabled`, `tabIndex` и блокировка события являются частью обязательного поведения и не
могут быть отменены случайным сочетанием native props.

## Дизайн-токены — контракт, а не подсказка по цвету

Компонент не подбирает похожий hex/rgb и не копирует значение токена вручную. Для каждого значимого варианта используется
точный токен из макета Admiral 3 и `@admiral-ds/admiral3-tokens`.

Цветовые токены подключаются через CSS custom property с fallback на текущую `styled-components` theme:

```css
color: var(--admiral-color-…, <значение из theme>);
```

Основной путь через CSS custom properties позволяет переключать тему атрибутом без обязательного React rerender и без
обязательного `ThemeProvider`. Fallback сохраняет работу в приложениях, которые используют theme object. Общий helper
`cssToken` не даёт каждому компоненту заново реализовывать эту развилку.

Типографика применяется готовым объектом `textStyles`, а не набором вручную выписанных `font-*`. Иначе часть связанного
типографического контракта легко забыть или рассинхронизировать при обновлении токенов.

Постоянные стили находятся в `styled-components` или локальных style helpers. Inline styles в компонентах и постоянной
demo-разметке запрещены, потому что они обходят общий способ темизации, сложнее поддерживают состояния и провоцируют
одноразовые значения вне токенов.

## Размеры хранятся числами, единицы добавляет владелец CSS

Размерные constants, которые участвуют в расчётах, хранятся как числа:

```ts
const parameters = { size: 10, horizontalPadding: 6 };
```

`px` добавляется в `style.ts`. Число можно безопасно использовать в геометрических расчётах и browser-тестах; строка
`'10px'` заставила бы каждый раз разбирать CSS-значение.

Внутренний визуальный элемент отвечает за собственные размеры и состояния, родитель — за композицию между детьми. Не
следует компенсировать неполную высоту control через случайный `min-height` на внешнем контейнере: ответственность должна
оставаться у элемента, который формирует эту геометрию.

## Сложные допустимые сочетания выражаются типами

Когда props зависят друг от друга, простой набор опциональных полей допускает невозможные комбинации. В `Button` union
разделяет варианты `solid`/`ghost` и `flat`/`outline`, поэтому обязательность `appearance` и допустимый `colorMode`
проверяются до запуска приложения.

Такой тип сложнее плоского интерфейса, но оправдан, если он исключает реальное некорректное состояние. Не нужно вводить
сложный conditional type только ради теоретической строгости: типизация должна делать контракт понятнее.

## Файлы разделены по ответственности

Типовой компонент состоит из нескольких небольших файлов:

```text
ComponentName/
  ComponentName.tsx       # React-поведение и DOM-композиция
  types.ts                # публичные и локальные типы
  constants.ts            # runtime-наборы вариантов и числовые параметры
  style.ts                # стили и token mappings
  index.ts                # поддерживаемый публичный API компонента
  ComponentName.test.tsx  # unit-контракт
  stories/                # документация и render templates
```

Для `BadgeDot` это действительно больше файлов, чем один старый `index.tsx`. Зато у каждого файла одна причина для
изменения, а review не смешивает DOM, таблицу токенов, публичные типы и документацию.

Разделение не означает «один helper — один файл». Дополнительный файл нужен, когда у него есть отдельная ответственность и
он делает основной код понятнее. Ненужная вложенность и абстракции противоречат KISS так же, как и монолитный компонент.

## Barrel — граница поддержки

Локальный `index.ts` экспортирует компонент, props и осознанные публичные типы. `style.ts`, `constants.ts`, styled props и
служебные helpers остаются внутренними.

Это важно не только для порядка в папках. Любой публичный экспорт становится обещанием совместимости: потребители начнут
импортировать его, и последующий рефакторинг станет breaking change.

Пакет предоставляет root import и явные component subpaths. Subpath нужен для потребителей, которым требуется точечный
entrypoint, а проверка consumer bundle гарантирует, что он не притягивает несвязанные компоненты. Deep import во внутренний
файл такой гарантии не имеет.

Stories и templates импортируют компонент через публичный API пакета. Благодаря этому примеры одновременно проверяют тот
же путь, которым будет пользоваться приложение, и не скрывают забытый export локальным импортом.

## `cssMixin` не является стандартным escape hatch

В `react-ui` встречается публичный `cssMixin`, позволяющий внедрить произвольный styled-components fragment внутрь
компонента. Для нового primitives-пакета это не базовый паттерн.

Такой escape hatch связывает потребителя с внутренней разметкой и порядком CSS, затрудняет изменение компонента и создаёт
состояния, которых нет в дизайне и visual-матрице. Сначала следует проверить обычную композицию, `className`, внешний
styled wrapper, CSS custom properties или небольшой семантический prop. Новый публичный mixin добавляется только при
подтверждённом повторяемом сценарии.

## Storybook, playground и тесты решают разные задачи

- **Unit-тест** проверяет React/DOM-контракт: defaults, ref, attributes, события и выбор варианта.
- **Storybook** документирует API, состояния и доступность.
- **Render template** содержит обычный React-код без зависимости от Storybook и может переиспользоваться.
- **Internal playground** даёт стабильный runtime для browser/e2e-сценариев без зависимости от Storybook.
- **E2E** проверяет то, что имеет смысл только в браузере: focus, keyboard, computed styles, геометрию и смену темы.
- **Visual regression** фиксирует конечную матрицу размеров, вариантов и состояний в воспроизводимом Linux Chromium.
- **Consumer bundle/package checks** проверяют уже собранный tarball, публичные entrypoints, декларации и tree shaking.

Не каждый Storybook-пример нужно дублировать в playground. Туда попадают только сценарии, необходимые для browser/e2e.
Но новый публичный вариант нельзя считать законченным, если он существует только в реализации и не покрыт подходящим
уровнем проверок.

## Когда можно отступить от паттерна

Паттерны нужны для одинаковых задач, а не для одинакового внешнего вида кода. Перед отклонением нужно ответить на вопросы:

1. Это публичный контракт или одноразовая внутренняя деталь?
2. Набор значений закрытый или потребитель действительно должен передавать произвольную строку?
3. Custom-настройка заменяет preset или независимо дополняет его?
4. Поле обязательно для осмысленной конфигурации или допустим частичный fallback?
5. Существующий native HTML API уже решает задачу?
6. Значение взято из точного дизайн-токена или подобрано вручную?
7. Новая абстракция уменьшает сложность сейчас, а не только обещает пользу когда-нибудь?
8. Изменение публичного API проверено через barrel, declarations и consumer entrypoint?

Если компоненту действительно нужен другой контракт, его нужно обосновать поведением и зафиксировать тестами. Копировать
форму соседнего компонента без проверки семантики так же неправильно, как игнорировать общий паттерн ради экономии
нескольких строк.

## Короткий checklist нового primitive

- Использован подходящий нативный элемент и передан ref.
- Размер по умолчанию — `m`.
- Закрытые варианты объявлены в `constants.ts` через `as const`, а union выведен из массива.
- Произвольный `string` не добавлен в `appearance`, `dimension`, `status` и аналогичные props.
- Custom-значения имеют именованный config и не попадают объектом в DOM.
- Styled-only props имеют префикс `$`; boolean `data-*` присутствуют только в активном состоянии.
- Использованы точные Admiral 3 tokens и готовые объекты типографики.
- Публичный barrel не экспортирует styles, constants и служебные типы.
- Story использует публичный импорт; playground добавлен только для нужного e2e-сценария.
- Проверены unit, browser, accessibility и необходимые visual-состояния.
- Запущены обязательные команды из `CONTRIBUTING.md`.
